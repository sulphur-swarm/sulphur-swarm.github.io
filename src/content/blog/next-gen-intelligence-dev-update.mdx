# Next-Gen Intelligence: Building the Architecture — Dev Update

In our [previous post](/blog/next-gen-intelligence), we described the architecture: a holistic intelligence system built around a JEPA vision encoder, a DreamerV3 RSSM world model, a Mamba-based reasoning core, and a continuous perceive→predict→decide→act loop — all targeting consumer-grade RTX hardware.

That was the vision. This post covers what we've built.

The first phase of implementation is complete. We have a working Python package, a functional WorldState latent bottleneck, a JEPAVisionEncoder with attention pooling, a DreamerV3 RSSM world model, a MambaReasoningCore, a wired-up processing loop, and an integration test harness that verifies the full stack on CPU. No GPU required to run the tests.

Here's how each piece came together.

## Python Package Scaffold

Before writing a single neural network layer, we established the package structure. A project this complex — multiple specialized models that need to compose cleanly — demands an architecture where configuration, components, and concerns are kept strictly separate.

The package layout follows a standard pattern:

```
next_gen_intelligence/
├── config/
│   ├── __init__.py
│   ├── intelligence_config.py   # Root typed config dataclass
│   ├── vision_config.py
│   ├── world_model_config.py
│   └── reasoning_config.py
├── models/
│   ├── world_state.py
│   ├── jepa_vision_encoder.py
│   ├── dreamer_rssm.py
│   └── mamba_reasoning_core.py
├── core/
│   └── intelligence_core.py     # Main processing loop
└── tests/
    └── test_integration.py
```

Configuration is handled via Python dataclasses backed by YAML. Each component gets its own typed sub-config:

```python
@dataclass
class IntelligenceConfig:
    vision: VisionConfig = field(default_factory=VisionConfig)
    world_model: WorldModelConfig = field(default_factory=WorldModelConfig)
    reasoning: ReasoningConfig = field(default_factory=ReasoningConfig)
    tick_rate_ms: int = 100
```

Loading is a single call: `IntelligenceConfig.from_yaml("config.yaml")`. Individual fields are typed, so invalid config values surface immediately at startup rather than causing mysterious failures mid-run.

Logging uses `structlog` throughout. Every log call emits structured JSON with a fixed schema — component name, log level, timestamp, and arbitrary key-value context. This makes logs grep-able and trivially parseable by downstream tooling, which matters for a system that runs continuously in the background.

## WorldState — Perceiver IO-style Latent Bottleneck

The central data structure of the architecture is `WorldState`: a fixed-size latent array that serves as the shared memory for all components.

The design is inspired by Perceiver IO. Instead of forcing every input modality into a single flat token sequence, we maintain a compact array of learned latent vectors — 512 latents at 256 dimensions each — and use cross-attention to read from and write to this array.

```python
class WorldState(nn.Module):
    def __init__(self, num_latents: int = 512, latent_dim: int = 256):
        super().__init__()
        self.latents = nn.Parameter(torch.randn(num_latents, latent_dim))
        self.cross_attn_write = CrossAttention(latent_dim)
        self.cross_attn_read = CrossAttention(latent_dim)

    def write(self, inputs: Tensor) -> None:
        """Cross-attend inputs into latent array, updating WorldState."""
        self.latents = self.cross_attn_write(self.latents, inputs)

    def read(self, queries: Tensor) -> Tensor:
        """Cross-attend queries against latent array, returning context."""
        return self.cross_attn_read(queries, self.latents)
```

The latent bottleneck solves a structural problem. Without it, you'd need every downstream component to accept arbitrary-length, modality-specific inputs — a vision encoder produces 196 patch embeddings, an audio encoder might produce 512 mel-spectrogram frames, a text tokenizer produces variable-length sequences. Every component would need to handle every possible input shape.

WorldState decouples all of that. Modality encoders write into the fixed-size latent array via cross-attention. Downstream components read from it via cross-attention. The shape contract is always 512×256, regardless of what was written.

A fixed footprint means memory consumption doesn't scale with input complexity. Feeding a high-resolution video frame doesn't blow up downstream memory usage — the bottleneck absorbs it.

## JEPAVisionEncoder — ViT-B/16 with Attention Pooling

The vision encoder uses a ViT-B/16 backbone — 86M parameters, 16×16 pixel patches, 224×224 input — pretrained with a JEPA objective rather than supervised classification or pixel reconstruction.

The JEPA training signal is more semantically useful than either of those alternatives. Rather than reconstructing pixels (which forces the model to spend capacity on low-level texture) or predicting class labels (which collapses rich visual content into a single category), JEPA predicts abstract representations of masked patch regions. The model must learn what matters semantically in order to predict the representations, not the pixels.

The standard ViT-B produces a sequence of 196 patch embeddings plus a CLS token. We replace the CLS aggregation with a learned attention pooling head:

```python
class AttentionPooling(nn.Module):
    def __init__(self, dim: int, num_heads: int = 8):
        super().__init__()
        self.query = nn.Parameter(torch.randn(1, 1, dim))
        self.attn = nn.MultiheadAttention(dim, num_heads, batch_first=True)

    def forward(self, patch_tokens: Tensor) -> Tensor:
        # query: (B, 1, D), keys/values: (B, 196, D)
        query = self.query.expand(patch_tokens.size(0), -1, -1)
        out, _ = self.attn(query, patch_tokens, patch_tokens)
        return out.squeeze(1)  # (B, D)
```

Attention pooling outperforms CLS aggregation on transfer benchmarks because it can learn task-specific aggregation weights. The CLS token is trained with a fixed position and attends to patches with a fixed interaction pattern learned during pretraining — attention pooling is more flexible.

The encoder output is a single `(B, 768)` embedding per image. This gets written into WorldState via a linear projection to 256 dims, then cross-attention write. VRAM footprint: approximately 0.35GB.

## DreamerV3 RSSM World Model

The Recurrent State Space Model (RSSM) is the temporal engine of the architecture. It maintains a continuous latent belief about the state of the world, updated at every tick.

The RSSM factorizes the world state into two components:

- **Deterministic state** `h_t`: a GRU hidden state that accumulates information over time. Deterministic and fully differentiable.
- **Stochastic state** `z_t`: a categorical latent sampled from a learned distribution. Provides representational capacity and supports imagination.

The update equations at each timestep:

```
h_t  = GRU(h_{t-1}, z_{t-1})
z_t  ~ Categorical(MLP(h_t, x_t))     # representation model (obs available)
ẑ_t  ~ Categorical(MLP(h_t))          # transition model (no obs, for imagination)
r̂_t  = MLP(h_t, z_t)                  # reward predictor
```

The DreamerV3 implementation includes three improvements over the original DreamerV2:

**Symlog encoding.** Reward and value targets are encoded via the symlog function — `sign(x) * log(|x| + 1)` — before feeding into prediction heads. This makes the model robust to reward distributions with very large magnitudes without manual reward scaling.

**Two-hot reward targets.** Scalar rewards are represented as soft two-hot vectors over a fixed set of buckets. This turns reward prediction into a classification problem over a learned distribution, which is more stable than direct regression.

**Free bits KL balancing.** The KL divergence between the representation model and the transition model uses a free-bits threshold: the KL loss is ignored for latents below a minimum information threshold. This prevents posterior collapse — the failure mode where the stochastic state `z_t` carries no information because the KL penalty dominates.

After each tick, the RSSM state `(h_t, z_t)` is projected to 256 dims and written into WorldState via cross-attention. This gives WorldState a continuously updated temporal belief, in addition to the perception-derived content from the vision encoder.

The RSSM is deliberately small: approximately 0.06GB VRAM. It runs continuously in the background, even when no new observations are arriving, rolling forward its transition model to anticipate what comes next.

## MambaReasoningCore

The reasoning layer is built on Mamba — a State Space Model designed for efficient long-sequence processing.

Transformers reason well but scale quadratically with sequence length. For a world model that maintains hundreds of latent entries and must reason across all of them at every tick, quadratic attention is expensive. Mamba uses selective state space mechanics to achieve linear-time sequence modeling without sacrificing the ability to selectively attend to relevant positions.

The core architecture is a stack of Mamba layers operating directly on the WorldState latent sequence:

```python
class MambaReasoningCore(nn.Module):
    def __init__(self, cfg: ReasoningConfig):
        super().__init__()
        self.layers = nn.ModuleList([
            MambaBlock(d_model=cfg.latent_dim, d_state=cfg.state_dim)
            for _ in range(cfg.num_layers)
        ])
        self.norm = nn.LayerNorm(cfg.latent_dim)

    def forward(self, world_state: Tensor) -> Tensor:
        # world_state: (B, 512, 256) — full latent array
        x = world_state
        for layer in self.layers:
            x = layer(x)
        return self.norm(x)  # reasoning trace: (B, 512, 256)
```

Mamba's selective scan gate allows each layer to decide how much of the previous state to propagate forward versus override with new input. This gives the reasoning core a form of soft attention across the latent array without the quadratic cost.

The output — a "reasoning trace" of the same shape as WorldState — is used to condition the language model's generation. Rather than prompting the LLM directly with world state latents (which are uninterpretable to it), the reasoning trace is projected into token-space and prepended to the context. The language model generates tokens conditioned on this compressed, reasoning-refined representation of the current world state.

VRAM footprint: approximately 0.75GB, making it the most memory-intensive component outside the language model itself.

## Processing Loop — Perceive → Predict → Decide → Act

The `IntelligenceCore` class wires the components into a continuous loop. Each tick takes approximately 100ms by default (configurable), and the loop runs asynchronously so inputs can interrupt at any phase.

```python
async def run(self) -> None:
    while self.running:
        tick_start = time.monotonic()

        # 1. Perceive
        obs = await self.sensor_hub.collect()
        if obs.image is not None:
            vision_embed = self.vision_encoder(obs.image)
            self.world_state.write(vision_embed)
        if obs.tokens is not None:
            text_embed = self.text_encoder(obs.tokens)
            self.world_state.write(text_embed)

        # 2. Predict
        self.rssm.step(self.world_state)  # advances h_t, z_t; writes to WorldState

        # 3. Decide
        reasoning_trace = self.reasoning_core(self.world_state.latents)

        # 4. Act
        if self.should_respond():
            output = await self.language_model.generate(reasoning_trace)
            await self.output_hub.emit(output)

        # Maintain tick rate
        elapsed = time.monotonic() - tick_start
        await asyncio.sleep(max(0, self.tick_rate_s - elapsed))
```

The loop is non-blocking at every phase. If new input arrives while the loop is in the Predict or Decide phase, it is queued and written to WorldState on the next Perceive phase. The system never blocks waiting for input.

The `should_respond()` gate prevents the Act phase from running every tick. It checks whether the reasoning trace has crossed an information-theoretic threshold — roughly, whether the world model believes there is something worth saying. This is the continuous-loop analogue of the request/response trigger.

## Integration Test Harness

The integration test suite lives in `tests/test_integration.py` and verifies the full stack end-to-end using synthetic inputs — no GPU, no real sensors required.

```python
@pytest.fixture
def dummy_frame() -> Tensor:
    return torch.randn(1, 3, 224, 224)

@pytest.fixture
def dummy_tokens() -> Tensor:
    return torch.randint(0, 50257, (1, 32))

def test_full_forward_pass(dummy_frame, dummy_tokens, default_config):
    core = IntelligenceCore(default_config)
    core.perceive(image=dummy_frame, tokens=dummy_tokens)
    core.predict()
    trace = core.decide()
    output = core.act(trace)

    assert core.world_state.latents.shape == (512, 256)
    assert core.rssm.h_t.shape == (1, default_config.world_model.deterministic_dim)
    assert trace.shape == (1, 512, 256)
    assert output.token_ids.shape[0] > 0
```

Additional test cases cover:

- **Config loading**: `IntelligenceConfig.from_yaml("tests/fixtures/default.yaml")` round-trips correctly
- **Structured logging**: log output contains expected fields (`component`, `level`, `timestamp`)
- **CPU-only initialization**: all components instantiate without CUDA; no GPU assertions in the test suite
- **WorldState write/read symmetry**: a written embedding can be approximately recovered via read cross-attention

Running the suite is a single command:

```bash
pytest tests/ -v
```

All tests pass on CPU. CI runs without GPU hardware. This was a deliberate design choice — the integration test suite is not a performance benchmark; it's a correctness harness.
